# 작업 4단계 계획: 행위 감지 개선 (개발 세트 넓히기)

- 작성: 2026-10-24 · 근거: [stage2_results_v1.md](stage2_results_v1.md), 결정 24
- 목표: engine-v1에서 드러난 **행위 감지 재현율 부족**을 평가 세트를 보지 않고 고친다.
  - 문제 신호: D2 0.18, P1 0.24, P2 0.06, R1 0.31, G3 0.11
- 끝 기준: 개선판(v1.1)을 **새 평가 세트(4-3)**와 기존 평가 세트에서 각각 한 번씩 돌려 v1과 비교한 표

## 1. 왜 개발 세트부터인가

v1이 놓친 이유는 규칙을 고칠 근거, 즉 표현의 폭이 개발 세트에 없었기 때문입니다. 개발 세트는 한 문체(모델이 쓴 합성 대화)로 33건뿐이었습니다. 평가 사례를 보고 표현을 넣으면 점수는 오르지만 아무것도 증명하지 못합니다. 그래서 **평가 사례가 아닌 곳에서 표현의 폭을 늘립니다.**

## 2. 새로 만드는 데이터

| 이름 | 만드는 사람 | 규칙 작성자(이 세션)가 보는가 | 쓰임 |
|---|---|---|---|
| **4-1 합성 2차** | ChatGPT·Gemini·Claude, 기억을 끈 새 대화 | 봄 | 개발 세트. 말투·길이·돌려 말하기를 일부러 다양하게 ([dev/05](dev/05_synthetic_round2_prompt.md)) |
| **4-2 공개 사례 재구성 (개발용)** | 이 세션 | 봄 | 개발 세트. 평가 10건과 **다른 출처**의 기사·판결문을 같은 방식(메시지별 출처 표시)으로 재구성. 평가 세트와 같은 문체를 개발 세트에도 갖추기 위함 |
| **4-3 새 평가 세트 (봉인)** | **다른 세션**(이 프로젝트 밖, 기억 끔) | **고정 전까지 보지 않음** | v1.1의 정직한 평가. 4-1·4-2·기존 평가 세트와 다른 출처 ([dev/06](dev/06_holdout_prompt.md)) |

### 4-3 봉인 방법
1. 다른 세션이 만든 파일을 사용자가 **저장소 밖**에 보관합니다.
2. 파일의 SHA-256 값만 저장소에 커밋합니다 (`docs/holdout_v2.md`). 규칙을 고치기 전에 평가 세트가 이미 정해져 있었다는 증거가 됩니다.
3. v1.1을 태그로 고정한 뒤에 파일을 저장소에 넣습니다. 커밋된 값과 같은지 확인한 다음 라벨링(기존 절차: 모델 3개 + 사용자 판정)과 평가를 진행합니다.

### 4-2가 피할 것
- 기존 평가 세트 10건의 출처 ([data-sources.md](data-sources.md))
- 봉인된 새 평가 세트 10건의 출처 주소와 **같은 사건을 다룬 다른 기사** ([holdout_v2.md](holdout_v2.md)). 예: 같은 조직·같은 피해 규모를 다룬 후속 보도

## 3. 규칙을 고치는 순서
1. 4-1·4-2로 개발 세트를 넓힙니다. 사기 대화에는 금전 지점만 이 세션이 표시합니다. 평가용 정답이 아니라 개발용 참고입니다.
2. 개발 세트에서 놓친 메시지와 잘못 붙은 메시지를 보고 행위 감지를 고칩니다. 고칠 때마다 `docs/dev/`에 바뀐 것과 근거가 된 개발 대화 ID를 남깁니다.
3. 정상 쪽은 합성 정상 대화와 AI-Hub Training 200건으로 오탐을 확인합니다. 흐름 판정 v1은 그대로 둡니다. 흐름 판정에 정답 신호를 넣으면 10/10이 나왔기 때문입니다 (결과 3.2).
4. 표현 조각과 평가 문장의 겹침 검사(`check_lexicon_leak.py`)를 매번 돌립니다.
5. `engine-v1.1` 태그로 고정합니다. 그다음 4-3 평가 → 기존 평가 세트 재실행(**"평가 후 수정"으로 표시**) 순서로 진행합니다.

## 4. 소형 모델(B안)은?
4-1·4-2가 모이면 신호 분류 모델을 학습할 데이터도 생깁니다. 규칙 v1.1 결과를 본 뒤에도 재현율이 부족하면 B안을 비교합니다 (plan.md 4.3).
