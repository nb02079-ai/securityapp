## 2. 왜 만드는가 (문제와 빈자리)

- 단일 문자 판별은 이미 여러 곳에서 제공한다: KISA 보호나라(URL 포함 문자), 케이뱅크 스미싱 AI 판독(LLM 기반), SKT 미끼문자 알림, 삼성 인텔리전스 차단.
- 최근 수법은 링크 없는 미끼문자로 접근한 뒤 카카오톡·텔레그램으로 옮겨 가 몇 주에 걸쳐 신뢰를 쌓고 돈을 요구한다(리딩방 투자사기, 로맨스 스캠).
- 대화 흐름 전체를 보는 도구는 구글 Messages의 대화형 사기 탐지가 가장 가깝지만 영어·Google Messages 한정이다. LG유플러스 익시오는 카카오톡 속 악성 URL·앱 설치를 탐지하지만 대화의 진행 단계는 보지 않는다.
- 조사 범위 안에서 **한국어 메신저 대화를 사기 단계 기준으로 분석하는 도구는 찾지 못했다.** (없다는 증명은 아니므로 진행 중에도 계속 확인)

### 2.1 왜 업로드 웹앱이 아니라 자동 감시 앱인가
- 대화 파일을 직접 올리는 방식은 **이미 의심하는 사람**만 쓴다.
- 이런 사기는 피해자가 끝까지 의심하지 않도록 설계돼 있어, 정작 필요한 사람에게 닿지 않는다.
- 그래서 의심이 필요한 시점을 "사기를 당하는 중"에서 **"평소에 가족과 함께 한 번 켜 두는 시점"**으로 옮긴다.

## 3. 범위

### 이번 버전에 넣는 것 (v2)
- 안드로이드 알림 접근 권한(NotificationListenerService)으로 카카오톡 알림 수집 — 1:1 대화와 단체방(리딩방) 모두
- 대화방별 메시지 누적 저장(기기 내 암호화 저장소)
- 위험 신호 감지(외부 앱 이동 유도·금전 요구·수익 보장·긴급성 압박·비밀 유지 요구·신원 위장 등)와 조합한 위험도 판정, 메시지가 들어올 때마다 갱신
- 판정 결과를 사용자에게 설명하는 단계 요약 — 출발 가설은 **접근 → 신뢰 형성 → 유도 → 금전 요구** 4단계였고, 작업 1단계 자유 메모 검토 결과 **돈을 받은 뒤 더 요구하기**를 다섯 번째로 추가했다 (5.2). 라벨링 결과로 다시 검증·수정한다
- 단계 도달 시 본인에게 경고 알림 + 앱 안에서 근거 문장과 이유 확인
- 가족 공유: 경고 화면의 버튼을 누르면 문자·카카오톡 공유 창이 열리고, 대화 내용 없이 "주의 단계 도달" 안내 문구만 채워진다 (사용자가 직접 보냄)
- 처음 켤 때 본인 동의 화면, 감시 대상 앱·대화방 선택, 언제든 끄기
- 재생 도구: 대화 파일(카카오톡 내보내기)을 알림처럼 한 줄씩 흘려 넣어 판정을 시험·평가하는 개발용 기능

### 다음 버전으로 미루는 것
- 텔레그램·문자(SMS) 알림 지원
- 이미지·음성 메시지 분석
- 소형 모델의 기기 내 재학습
- 플레이스토어 정식 출시 (이번 버전은 APK 직접 설치로 시험)

### 범위 밖 (하지 않는 것)
- 접근성 서비스(AccessibilityService)로 화면 읽기 — 권한이 과하고 정책상 제한이 커서 사용하지 않음
- 메시지 자동 차단·삭제, 상대방 신고 자동화
- iOS 지원 — 다른 앱의 알림을 읽는 방법이 없어 불가

## 4. 기술 설계 (초안, 중간 점검 1차 전 확정)

### 4.1 처리 흐름
```
[카카오톡 알림 도착]
  → 알림 수신기: 앱 이름·대화방 이름·보낸 사람·메시지·시각 추출
  → 필터: 감시 대상 앱/대화방인지, 최근 새로 생긴 대화 상대인지 표시
  → 기기 내 저장소: 대화방별 메시지 누적 (암호화)
  → 판정 엔진: 새 메시지에서 위험 신호 감지 → 대화방 위험도 갱신 → 단계 요약으로 변환
  → 단계 상승 시: 본인 경고 알림 → (사용자가 원하면) 공유 버튼으로 가족에게 단계 안내 직접 전송
  → 앱 화면: 대화방 목록·단계 타임라인·근거 문장
```

### 4.2 판정 엔진 설계 원칙
- **누적형(스트리밍) 판정**: 대화 전체를 한 번에 보는 게 아니라 메시지가 하나씩 들어올 때마다 상태를 갱신한다.
- **엔진은 안드로이드와 분리된 순수 Kotlin 모듈**로 만든다 → PC(JVM)에서 평가 세트를 그대로 돌려 수치를 내고, 앱에도 같은 코드를 넣는다. 평가 결과와 실제 앱 동작이 어긋나지 않게 하기 위함.
- **순서 있는 단계가 아니라 독립적인 위험 신호로 판정한다**: 각 신호를 따로 감지하고, 신호의 조합·누적으로 위험도를 낸다. 단계는 그 결과를 사람이 이해하기 쉽게 설명하는 표현으로만 쓴다.
  - 이유: 실제 사기는 신뢰 형성 없이 바로 돈을 요구하거나, 금전 요구 뒤 다시 신뢰 쌓기로 돌아가는 등 순서가 일정하지 않다. 단계 순서를 가정한 엔진은 이런 경우를 놓친다.
  - 단체방(리딩방)은 여러 발신자의 신호를 대화방 단위로 합산하고, 발신자별 신호도 따로 기록한다.
- 신호 목록과 단계 체계는 고정된 정답이 아니라 **가설**이며, 작업 1단계의 사례 검토 결과에 따라 추가·삭제·병합한다.
- **단어보다 흐름·행동 신호를 중심에 둔다**: 새로 생긴 대화 상대, 다른 앱·방으로 옮기자는 요구, 요구 금액의 증가, 가족·지인에게 숨기라는 요구, 출금하려면 돈을 더 내라는 요구처럼 대화의 흐름에서 드러나는 신호를 우선한다. 특정 단어 목록은 보조로만 쓴다.
  - 근거: 가짜 리뷰 탐지 연구(ICWSM 2013)에서, 사람이 만든 가짜 리뷰로는 단어 특징이 잘 통했지만 실제 가짜 리뷰에서는 약했고 행동 특징이 잘 통했다. 우리 평가 세트의 사기 대화도 재구성본이라 같은 위험이 있다(6.3 참고).

#### 4.2.1 판정 구조: 행위와 흐름의 두 층
```
[메시지 1개]  → ① 행위 감지: 이 말이 무엇을 하려는가 (여러 개 가능)
[대화방 상태] → ② 흐름 판정: 지금까지 나온 행위의 조합·순서·증가 → 관찰 / 주의 / 경고
```
- 단어는 행위를 찾는 재료일 뿐이고, 판정은 행위가 쌓인 모양으로 한다.
- 행위 감지는 처음엔 규칙으로, 흐름 판정은 대화방마다 상태를 갖는 작은 상태 기계로 만든다.
- **v1은 대화방 단위로 판정한다.** 실제 사기는 여러 방에 나뉘어 진행된다(재구성 사례 01: 리딩방에서 신뢰 형성 → 비서 1:1에서 입금 계좌 → 고객센터 1:1에서 보증금 요구). 여러 방을 하나의 "관계 묶음"으로 합쳐 판정할지는, 방 하나만으로 얼마나 잡히는지 확인한 뒤(작업 3단계) 정한다.

#### 4.2.2 신호 체계 (가설 v2 — 자유 메모로 1차 수정, 라벨링과 일반 대화 43건으로 추가 검증)
v1 가설을 세 모델(Grok·Claude·ChatGPT)의 자유 메모와 대조해 고쳤다 ([docs/labeling/02_free_memo_analysis.md](labeling/02_free_memo_analysis.md)). "자유 메모" 칸은 세 모델 중 몇 개가 이 행동을 따로 묶었는지다.

| 분류 | 신호 | 예시 모습 | 알림으로 보이나 | 오프라인 평가 | 자유 메모 |
|---|---|---|---|---|---|
| 관계 | 새로 생긴 대화 상대 | 앱이 처음 본 지 며칠 안 됨 | 예 | **제외** (4.2.4) | 글자로 안 보임 |
| 관계 | 단체방 다수 발신자의 맞장구 | 여러 명이 같은 수익 인증 반복 | 예 | 일부 | 3/3 |
| 관계 | 친밀감 쌓기 (감정 급진전 포함) | 안부·일상·호의, 짧은 기간에 사랑·운명 | 예 | 예 (**맥락 전용**, 4.2.3의 5) | 2/3 (감정 급진전 단독은 0/3) |
| 요구 | 채널 이동 요구 | 다른 앱·방·링크로 옮기자 | 예 | 예 | 1~2/3 (근거 약함) |
| 요구 | 투자금 입금 요구 | 이 사이트·지갑에 넣어라, 매수해라 | 예 | 예 | 3/3 (쪼갬) |
| 요구 | 대납·차용·선납 요구 | 통관비·배송비·급전을 대신 내 달라, 빌려 달라, 받으려면 먼저 내라(가입비·수수료 선납) | 예 | 예 | 3/3 (쪼갬), 선납은 개발 세트에서 추가 |
| 요구 | 지정 계좌·경로 통제 | 개인 계좌·지갑으로, ATM으로만, 창구 송금 금지 | 예 | 예 | 2/3 |
| 요구 | 출금 조건부 추가 입금 | 빼려면 수수료·보증금을 더 내라 | 예 | 예 | 3/3 |
| 요구 | 비밀 유지·고립 요구 | 가족에게 말하지 마라 | 예 | 예 | 3/3 |
| 요구 | 개인정보·앱 설치 요구 | 신분증, 주소, 계정, 원격 제어 앱 | 예 | 예 (금전 지점에는 넣지 않음) | 1/3 (근거 약함) |
| 설득 | 수익 보장·위험 부정 | 원금 보장, 무조건 오른다, 손실 보상 약속 | 예 | 예 | 3/3 |
| 설득 | 권위·신분 과시 | 전문가 경력, 사칭, 위조 서류, 증거 사진 | 예 | 예 | 3/3 |
| 설득 | 긴급성·한정성 압박 | 오늘만, 선착순, 마감, 급한 사정 | 예 | 예 | 3/3 |
| 설득 | 만남·확인 회피 | 영상통화·만남을 계속 미룸 | 상대 변명만 | 예 | 1/3 (근거 약함) |
| 진행 | 소액 선보상 | 작은 수익·손실 보상금·선물을 먼저 실제로 줌 | 예 | 예 | 3/3 (**새로 추가**) |
| 진행 | 화제 급전환 | 일상·다른 목적 대화에서 갑자기 돈·투자로 | 예 | 예 (흐름 판정 층에서만) | 첫 이상 신호 이유로 반복 (**새로 추가**) |
| 진행 | 요구 금액 증가 | 소액 → 큰 금액, 대출 권유, 복잡한 분배 규칙 | 예 (숫자 추출) | 예 | 3/3 |
| 진행 | 요구 반복 | 거절 후 다시 요구, 멈추지 못하게 붙잡기 | 예 | 예 | 2/3 |
| 진행 | 진행 속도 | 첫 연락부터 요구까지 기간 | 예 (알림 시각) | **제외** (시각 정보 없음) | 시각 정보 없음 |

- v1에서 바뀐 것: 금전 요구를 세 가지(투자금 입금 / 대납·차용 / 지정 계좌·경로 통제)로 나눔, 감정 급진전을 친밀감 쌓기에 합침, 소액 선보상·화제 급전환 추가.
- 근거 약함(1~2/3)으로 표시한 신호는 라벨링 결과와 일반 대화 오탐을 보고 유지·삭제를 정한다.
- 사례 유형에 가까운 행동(피해 회복 빙자 등)은 신호에 넣지 않고 사례 메타에 남긴다.

#### 4.2.3 판정 원칙
1. 행위 하나로는 경고하지 않는다 (금전 요구만으로는 친구 간 돈 빌리기와 구별되지 않음).
2. 경고는 **"요구" 행위 + 다른 분류 행위의 조합**이 있을 때만 낸다. 예: 수익 보장 → 이동 요구 = 주의, 여기에 투자금 입금 요구 + 금액 증가 = 경고.
3. 경고에는 감지된 행위 이름과 근거 문장을 함께 보여 준다.
4. 오래된 신호의 약화는 평가 데이터에 시각 정보가 없으므로 **메시지 수 기준**으로 시작하고, 실기기 단계에서 시간 기준을 검토한다.
5. **친밀감 쌓기는 맥락 전용**이다: 정상 대화에도 흔해 단독으로도, 2번 조합의 "다른 분류"로도 세지 않는다. 화제 급전환을 판단할 때 앞 맥락으로만 쓴다.

#### 4.2.4 오프라인 평가에서 관계·시간 신호를 빼는 이유
- AI Hub 일반 대화는 모두 아는 사이, 재구성 사기 대화는 모두 모르는 사이다. "새 상대" 신호를 넣으면 정답을 알려 주는 것과 같아 성능이 부풀려진다.
- 평가 데이터에는 메시지 시각이 없어 진행 속도를 공정하게 잴 수 없다.
- 따라서 오프라인 평가는 텍스트 행위·흐름만으로 하고, 관계·시간 신호의 효과는 실기기 평가(작업 5단계)에서만 측정한다.

### 4.3 판정 방식 후보
| 방식 | 장점 | 단점 |
|---|---|---|
| A. 규칙 + 가중치 점수 | 설명이 쉽고 가벼움, 배터리 부담 적음 | 표현이 바뀌면 놓침 |
| B. 기기 내 소형 한국어 분류 모델 (LiteRT 또는 ONNX Runtime Mobile) | 표현 변화에 강함 | 모델 크기·추론 시간·배터리, 학습 데이터 필요 |
| C. 외부 LLM API | 성능 높음 | **대화가 기기 밖으로 나감 → 핵심 원칙 위배, 제외** |

- 우선 **A로 동작하는 버전을 먼저 만들고**, 평가 결과를 보고 B를 추가해 A 대비 개선 폭과 배터리·지연 비용을 함께 측정한다.

### 4.4 알림 수집에서 확인해야 할 기술 문제
- 카카오톡 알림에서 대화방 이름·보낸 사람·본문이 어떤 필드로 들어오는지 (실기기 확인)
- 긴 메시지가 잘리는지, 여러 메시지가 묶여 오는 경우 중복 없이 나누는 방법
- 사용자가 카카오톡을 열고 있어 알림이 안 뜨는 동안의 메시지 누락 → 누락 가능성을 화면에 명시
- 대화 상대가 "연락처에 없는 사람"인지 알 수 없음 → 앱이 처음 본 시각을 기준으로 "최근 새로 생긴 대화"를 구분
- 제조사별 배터리 최적화로 백그라운드 서비스가 꺼지는 문제
- 내가 보낸 메시지는 알림으로 오지 않음 → 상대방 메시지만으로 판정하도록 규칙 설계

### 4.5 가족 공유 (B안으로 결정)
- **결정**: 앱이 자동으로 가족에게 신호를 보내지 않는다. 경고 화면의 "가족에게 알리기" 버튼을 누르면 안드로이드 공유 창(문자·카카오톡 등)이 열리고, 사용자가 직접 보낸다.
- 채워지는 문구는 "대화방 별칭 + 도달 단계 + 시각 + 확인 권유"로 한정하고, 대화 원문·상대 이름은 넣지 않는다.
- **이유**: 앱에 인터넷 권한을 넣지 않아도 되므로 "대화가 밖으로 나가지 않는다"를 누구나 권한 목록으로 확인할 수 있고, 서버·키 관리·신호 위조라는 공격면이 통째로 사라진다.
- **포기한 것**: 본인이 버튼을 누르지 않으면 가족이 모른다. 7.2의 대상자 반응 확인에서 이 방식이 충분한지 함께 묻는다.
- 자동 가족 신호(A안: 짝지은 기기 간 암호화·서명된 푸시)는 다음 버전 후보로 남긴다.

### 4.6 기술 스택 (잠정)
- 앱: Kotlin, Jetpack Compose
- 기기 내 저장: Room + 암호화(SQLCipher 등 후보)
- 판정 엔진: 순수 Kotlin 모듈 (JVM 단위 테스트·평가 실행)
- 모델 실행(B안): LiteRT 또는 ONNX Runtime Mobile
- 가족 공유: 안드로이드 기본 공유 인텐트 (네트워크 라이브러리 사용 안 함)
- 데이터 전처리·라벨링·모델 학습: Python
- 저장소: GitHub

### 4.7 보안 설계

이 앱은 "남의 메시지를 읽는 앱"이므로, 보안은 부가 기능이 아니라 앱이 존재해도 되는 이유를 지키는 부분이다.

#### 4.7.3 보안 검증 방법
대책은 "했다"가 아니라 "확인했다"로 보여 준다.
- 설치된 앱의 권한 목록에 인터넷 권한이 없음을 캡처로 확인
- MobSF 등 모바일 정적 분석 도구로 APK를 점검하고 결과 첨부
- 지정 앱이 아닌 시험용 알림(가짜 인증번호 알림 등)을 보내고 저장소에 남지 않는지 테스트
- 백업 시도, 로그 검색으로 메시지 내용이 새지 않는지 확인
- 앱 데이터 폴더를 직접 열어 봐도 암호화돼 읽을 수 없음을 확인

### 5.2 데이터 구성

| 세트 | 구성 | 목표 규모 | 원칙 |
|---|---|---|---|
| **평가 세트 (사기)** | 뉴스·금감원·경찰청 보도자료·판결 요약에 공개된 사례의 단계 흐름과 인용 문구를 뼈대로 재구성 (공개 출처에 전체 대화는 없음을 확인, "사기 사례 출처 목록" 문서 참고) | 10건부터 시작, 30건 내외 목표 | 메시지마다 출처 표시(인용 / 서술 기반 / 연결), 위험 신호는 연결 메시지에 쓰지 않음, 실명·계좌·연락처 제거 |

- 평가 세트는 "메시지 한 줄 = 알림 하나" 형태로 저장해, 재생 도구로 실제 앱과 같은 흐름에서 평가한다. 재구성 사기 대화는 메시지마다 방(room)·보낸 사람·본인 여부·출처 표시(인용/서술 기반/연결)를 함께 저장한다.
- 사진 메시지는 알림에 "사진"으로만 보이므로 재구성에서도 `[사진]`으로만 남긴다 (수익 인증 캡처 등은 글자로 판정할 수 없음).
- 상대방 메시지만 보이는 실제 조건을 반영해, 평가 때도 사용자 본인 메시지를 지운 버전을 함께 돌린다.
- **단계 체계 검증 후 라벨링**: 4단계(접근 → 신뢰 형성 → 유도 → 금전 요구)는 가설로만 두고, 라벨링 전에 아래 순서로 검증한다.
  1. 실제 사례 10건을 단계 없이 자유롭게 읽으며, 메시지마다 "무엇을 하려는 말인지" 메모한다 (영어 벤치마크의 유형 정의는 참고만 함) — **완료**: 사례를 쓰지 않은 세 모델(Grok·Claude·ChatGPT, 무료 기본 모델)이 가림판으로 메모 (2026-10-21, `docs/labeling/`)
  2. 메모를 묶어 위험 신호 목록을 만들고, 4단계 가설에 얼마나 들어맞는지 확인한다 — **완료**: 신호 체계 v2(4.2.2), 다섯 번째 단계 "돈을 받은 뒤 더 요구하기" 추가 (10건 중 8건이 첫 송금 뒤에도 이어짐)
  3. 잘 안 맞으면 단계·신호를 고친 뒤 라벨 기준표를 확정한다 — 진행 중
- 라벨은 두 층으로 붙인다: **메시지별 위험 신호**(여러 개 가능)와 **대화의 금전 지점 세 개**. 단계 라벨은 보조로 붙이고, 어느 단계에도 맞지 않으면 "분류 불가"로 남겨 건수를 기록한다.
  - **첫 금전 권유**: 상대가 돈을 쓰라고 처음 권한 메시지 (금액·계좌 같은 구체 지시가 없어도 됨). **피해자 본인 증권 계좌에서 특정 종목을 사라는 안내도 포함** — 앱은 투자 금액을 알 수 없고, 본인 계좌에서 손해가 나는 수법(운영자가 미리 사 둔 종목 매수 유도)도 있기 때문 (v2.8)
  - **첫 송금 의사 직전**: 피해자가 처음 돈을 보내겠다고 밝히거나 보내는 방법을 물은 메시지 직전의 상대 메시지 ("해 볼게요", "어떻게 참여하나요?") (v2.8)
  - **첫 송금 직전**: 피해자의 돈이 처음 **피해자 계좌 밖으로** 나가기 직전의 상대 메시지. 본인 증권 계좌 안의 매매와 "해 볼게요" 같은 의사 표현은 송금이 아니다. 송금 말이 없어도 뒤의 말로 앞선 송금이 분명하면 그 송금이 있었을 마지막 송금 지시로, 송금이 끝까지 없는 사례는 금액·계좌·주소 중 하나라도 정한 상대의 첫 구체 송금 지시로 대신한다. 송금 여부는 "보냈어요" 같은 말로 자동 판단하면 틀리므로(이메일·캡처를 보낸 경우) 사람이 붙인다
  - 정의 전체와 예시는 라벨 기준표 `docs/labeling/03_label_guide.md` (v2)
  - 개인정보 요구는 금전 지점에 넣지 않고 신호로만 붙인다
- **라벨은 재구성을 다 마친 뒤 완성본만 보고 붙인다.** 쓰면서 의도한 단계를 그대로 라벨로 쓰지 않는다. (근거: 합성 스미싱 데이터셋 연구에서 생성할 때 붙인 라벨의 약 절반이 실제 내용과 맞지 않았음)
- **두 번째 라벨러**: 재구성 사례 중 최소 5건은 다른 사람(지인 또는 별도 Claude 세션)이 출처와 완성본만 보고 독립적으로 라벨링하고, 금전 지점 세 개·위험 신호의 일치율을 보고한다. 자유 메모에서 의견이 갈린 사례(사례 06)는 반드시 포함한다. 실제 진행: 서로 다른 회사 모델 3개(Grok·Claude·ChatGPT)가 10건 전부, 사용자가 5건을 라벨링하고, 신호·단계는 모델 다수결, 셋이 다른 칸과 금전 지점은 사용자가 정한다. 사례 작성 세션은 최종 라벨을 정하지 않는다. (근거: ConScamBench는 80건 이중 라벨링으로 κ 0.89를 보고)
- 평가 세트는 처음 만든 뒤 잠그고, 규칙이나 모델을 고치면서 평가 세트를 보지 않는다. 사기 대화 재구성은 엔진 규칙을 만들기 전에 끝내고 잠근다.
- AI Hub 등 재배포 금지 데이터는 저장소에 올리지 않고, 내려받는 방법과 전처리 스크립트만 공개한다.
- 각 데이터의 출처와 활용 사실을 README에 명시한다.

## 6. 평가 방법

### 6.1 오프라인 평가 (평가 세트 재생)

주 지표는 단계 정의가 바뀌어도 그대로 유효한 것으로 정한다. 단계 체계가 수정돼도 검증이 흔들리지 않게 하기 위함이다.

**주 지표**
- **송금 전 경고율**: 사기 대화 중 **첫 송금 직전 메시지까지(그 메시지에서 낸 경고 포함)** 경고한 비율 (v2.6까지 "금전 요구 이전 경고율")
  - 그 메시지의 경고를 인정하는 이유: 경고는 메시지가 도착할 때 뜨므로, 사용자는 그 메시지를 보고 송금하기 전에 경고를 본다. "이전에"로 두면 사례 04·08처럼 요구 메시지 자체가 첫 이상 신호인 사례는 어떤 엔진도 성공할 수 없다 (세 모델 모두 이상 신호 = 요구 메시지로 봄)
- **조기 경고율**: 같은 기준을 **첫 금전 권유** 메시지에 적용한 비율 (권유를 받는 순간까지 경고했는가)
- **경고 시점**: 첫 송금 직전 메시지보다 몇 메시지 앞서 경고했는지 (빠를수록 좋음)
- **오탐률**: 일반 대화를 사기로 판정한 비율 — 가장 중요하게 본다 (가족 대화를 사기로 몰면 신뢰를 잃고 앱을 끈다)
- **미탐률**: 사기 대화를 첫 송금 직전 메시지까지 놓친 비율
- **지연 감점 지표 (ERDE 방식)**: 맞게 경고해도 늦을수록 감점하고, 첫 송금 직전 메시지를 넘기면 놓친 것으로 처리하는 단일 점수. 조기 위험 탐지 대회 eRisk에서 쓰는 방식을 따른다.
- **3단 비교 (같은 평가 세트, 같은 지표)**
  1. 단어 기준선: 금전 단어가 나오면 경고
  2. 행위 단독: 행위가 하나라도 감지되면 경고
  3. 행위 + 흐름: 4.2.3 규칙
  - 1↔2 차이 = 행위 감지의 효과, 2↔3 차이 = 흐름 판정의 효과
- 오프라인 평가에서는 관계·시간 신호를 쓰지 않는다 (4.2.4).
- **여러 방에 걸친 사례의 집계**: 사례 단위 결과는 "사례의 방 중 하나라도 첫 송금 직전 메시지까지 경고했는가"로 계산하고, 방 단위 결과(어느 방에서 잡혔는지)를 함께 기록한다. 방 단위 결과는 여러 방 묶음 판정이 필요한지 판단하는 근거가 된다. 일반 대화는 방 하나가 곧 사례다.

**보조 지표**
- **위험 신호 감지 정확도**: 메시지별 신호 라벨과 엔진 감지 결과의 일치도 (어떤 신호에서 약한지 파악용)
- **결심 전 경고율**: 같은 기준을 **첫 송금 의사 직전** 메시지에 적용한 비율 (피해자가 보내겠다고 마음먹고 말하기 전에 경고했는가). 마감점은 첫 송금 의사 직전과 첫 송금 직전 중 **앞선 쪽**으로 한다 (송금이 없는 사례에서 의사 표현이 구체 지시보다 늦게 나오는 경우 때문) (v2.8)
- **라벨러 간 일치율**: 라벨러 간 금전 지점 세 개·위험 신호·단계 일치율 (평가 세트 자체의 신뢰도). 회차별로 모두 기록
- **출처 종류별 성능**: 재구성 대화 성능과 금감원 실제 캡처 조각에서의 신호 감지 성능을 나눠 보고
- **단계 요약 일치율**: 사람이 붙인 단계 라벨과의 일치 비율 ("분류 불가" 건수와 함께 기록)
- **상대 메시지만 볼 때의 성능 저하 폭**
- **순서가 뒤섞인 사례에서의 성능**: 신뢰 형성 없이 바로 금전 요구하는 등 가설 순서와 다른 대화만 따로 모아 주 지표 계산

### 6.2 실기기 평가
- **하루 평균 오경고 횟수**: 실사용자 3명, 2주 (정상 생활에서 사기 경고가 몇 번 잘못 뜨는지)
- **배터리 사용량**: 앱 설치 전후 하루 배터리 소모 비교
- **판정 지연**: 알림 도착부터 판정 완료까지 시간
- **알림 누락률**: 시험용 대화를 보냈을 때 수집된 메시지 비율
- **사용자 피드백**: 경고를 이해했는지, 근거가 납득됐는지, 감시받는 느낌이 들었는지, 가족 공유 버튼을 실제로 누를 것 같은지
- **보안 검증**: 4.7.3의 항목을 모두 수행하고 결과를 기록

### 6.3 참고한 연구와 가져온 장치

| 연구 | 우리 계획에 가져온 것 |
|---|---|
| ConScamBench (arXiv 2607.11707, 2026) | 실제 공개 사례 중심 + 소량 합성 + 정상인데 헷갈리는 대화 구성, 사기 실행 전 구간만 평가, 이중 라벨링과 일치도 보고, 실제·합성 성능 분리 보고 |

| eRisk 조기 위험 탐지 (ERDE 지표) | 메시지를 하나씩 흘려 넣는 평가, 늦은 경고 감점 지표 |

## 7. 진행 순서와 일정

### 7.1 원칙: 검증 먼저, 앱은 마지막

> 표기: 이 문서에서 **"작업 N단계"**는 아래 진행 순서를, **"4단계 가설"**은 출발점이 된 사기 흐름(접근 → 신뢰 형성 → 유도 → 금전 요구)을 뜻한다. v2.7부터 설명용 단계는 여기에 "돈을 받은 뒤 더 요구하기"를 더한 다섯 단계다.

앱을 먼저 만들면 "알림은 잘 모이는데 판정이 쓸모없는" 상태를 늦게 알게 된다. 그래서 **판정이 실제로 의미가 있는지를 먼저 확인하고**, 통과했을 때만 안드로이드 앱에 붙인다. 판정 엔진은 처음부터 앱과 분리된 모듈이라, 순서를 바꿔도 다시 만들 부분이 없다.

| 단계 | 하는 일 | 끝났다는 기준 |
|---|---|---|
| 1. 데이터·단계 체계 검증·라벨 기준 | 실제 사례 10건으로 4단계 가설·위험 신호 목록 검증 및 수정(5.2), 라벨 기준표 작성, 평가 세트(사기 30건 내외·일반 30~60건) 구축 후 잠금, 개발 세트 준비 | 단계 체계 검증 결과 기록, 평가 세트 잠금, 라벨 기준표 문서화 |
| 2. 판정 엔진 + 재생 평가 | 규칙 기반 엔진(순수 Kotlin), 메시지를 하나씩 흘려 넣는 재생 평가기, 비교용 기준선 | 평가 세트 전체를 자동으로 돌려 지표 표가 나옴 |
| 3. 의미 검증 (판단 지점) | 기준선 대비 성능 비교, 실제 대상자 반응 확인 → 7.2 기준으로 계속/전환 결정 | 판단 결과와 근거를 문서로 남김 |
| 4. 엔진 개선 (선택) | 작업 3단계에서 부족한 부분 보완, 필요 시 소형 모델(B안) 비교 | 개선 전후 지표 비교표 |
| 5. 안드로이드 앱 적용 | 알림 수집, 기기 내 저장, 경고·근거 화면, 동의 화면, 가족 공유 버튼, 4.7 보안 대책 | 실기기에서 재생·실사용 평가와 보안 검증(6.2·4.7.3) 수행 |

### 7.2 의미 검증 기준 (작업 3단계 판단 지점, 잠정)

"의미가 있다"를 아래 세 가지로 판단한다. 숫자는 평가 세트를 만든 뒤 한 번 조정할 수 있지만, **엔진 결과를 보기 전에 확정한다.**

1. **단순한 방법보다 확실히 나은가**
   - 기준선: 대화 전체에서 "송금·입금·계좌·투자·수익" 같은 금전 단어가 나오면 경고하는 단순 키워드 방식
   - 엔진이 기준선보다 오탐률이 뚜렷하게 낮거나, 경고 시점이 뚜렷하게 빨라야 한다. (기준선과 비슷하면 위험 신호 조합 판정을 할 이유가 없음)
   - 6.1의 3단 비교에서 "행위 + 흐름"이 "행위 단독"보다 나아야 흐름 판정을 유지한다. 차이가 없으면 흐름 판정을 단순화한다.
2. **실제로 쓸 수 있는 수준인가** (잠정 수치)
   - 일반 대화 오탐률 10% 이하
   - 사기 대화 중 첫 송금 직전 메시지까지(그 메시지 포함) 경고한 비율(송금 전 경고율) 70% 이상
   - 상대 메시지만 볼 때도 위 수치에서 크게 떨어지지 않을 것
3. **대상자에게 경고가 통하는가**
   - 부모님 세대 3~5명에게 실제 사례를 재구성한 대화와 경고 화면 예시를 보여 주고, 경고를 이해했는지·멈추겠다고 답하는지·불쾌하거나 감시받는 느낌이 드는지 확인
   - 가족 공유 방식(본인이 버튼을 눌러 직접 알림)이 충분한지, 당사자와 자녀 양쪽의 의견 확인

**판단 결과에 따른 다음 행동**
| 결과 | 다음 행동 |
|---|---|
| 1·2·3 모두 통과 | 작업 5단계(앱 적용)로 진행 |
| 2만 미달 | 작업 4단계(엔진 개선)를 먼저 하고 다시 판단 |
| 1 미달 (기준선과 차이 없음) | 위험 신호 조합 판정 대신 더 단순한 경고 방식으로 범위를 줄이거나 주제 재검토 |
| 3 미달 (경고가 통하지 않음) | 자동 감시보다 가족이 함께 보는 방식 등 전달 방법을 바꿔 재설계 |

| 최종 제출 | 작업 5단계 앱 APK · 평가 결과 표 · 실기기 평가 기록 · 시연 영상 · 자기소개 사이트 연결 |

- 앱 적용이 마지막이라 실사용 2주 평가를 다 채우지 못할 수 있다. 그럴 경우 실사용 기간을 줄이고, 재생 평가와 시연 영상으로 앱 동작을 보여 준 뒤 실사용 결과는 이후 갱신한다.

## 8. 위험 요소와 대응

| 위험 | 대응 |
|---|---|
| 한국어 메신저형 사기 데이터가 공개돼 있지 않음 (조사로 확인) | 평가 세트는 공개 사례 재구성 30건 내외로 작게 유지, 개발에는 보이스피싱 전사·영어 벤치마크·합성 대화를 쓰되 평가에 섞지 않음 |
| 데이터 라이선스 위반 (재배포 금지 등) | 비상업 데이터는 저장소에 올리지 않고 전처리 스크립트만 공개, 출처 명시 |
| 안드로이드 개발 경험 부족으로 일정 지연 | 앱은 작업 5단계로 미뤘으므로, 그 전까지 Kotlin은 엔진 모듈 작성으로 먼저 익힌다. 앱 화면은 최소 구성으로 시작 |
| 앱 단계에서 알림 수집이 생각보다 어렵다고 늦게 밝혀짐 | 엔진은 앱과 분리돼 있어 대화 파일 분석 방식(v1 웹앱 구조)으로 되돌려도 결과가 남음. 여유가 있으면 작업 2~3단계 중 하루 정도 알림 구조만 찍어 보는 시험으로 위험을 미리 줄임 |
| 의미 검증 기준을 결과에 맞춰 바꾸고 싶어짐 | 7.2 기준을 엔진 결과를 보기 전에 확정하고 변경 기록에 남김 |
| 미리 정한 4단계가 실제 사기 흐름과 맞지 않음 (순서 뒤섞임·단계 건너뜀·단체방 구조) | 4단계는 가설로만 두고 작업 1단계에서 실제 사례로 검증·수정, 엔진은 순서 없는 위험 신호 기반, 주 지표는 단계 정의와 무관한 지표로 설정 |
| 재구성 대화로만 평가해 단어 규칙 성능이 실제보다 좋게 나옴 | 위험 신호는 연결 메시지에 쓰지 않음, 흐름·행동 신호 중심 설계, 단어 기준선과 비교, 실제 캡처 조각 성능을 따로 보고, 한계를 결과 옆에 명시 |
| 같은 틀로 라벨을 붙이고 평가해 틀 자체가 검증되지 않음 | 라벨링 전에 단계 없이 사례를 먼저 읽는 절차를 두고, "분류 불가" 건수와 순서가 뒤섞인 사례의 성능을 따로 보고 |
| 카카오톡 알림 형식이 버전마다 바뀌거나 정보가 부족함 | 실기기에서 알림 구조를 먼저 기록해 테스트 케이스로 고정, 파싱 실패 시 해당 메시지는 판정에서 제외하고 표시 |
| 알림이 안 뜨는 상황(앱 열람 중·알림 끔)의 메시지 누락 | 누락 가능성을 사용자에게 명시, 누락률을 평가 지표로 측정 |
| 제조사 배터리 최적화로 감시가 꺼짐 | 설정 안내 화면 제공, 서비스가 꺼졌을 때 본인에게 알림 |
| 정상 대화를 사기로 판정해 관계를 해침 | 오탐률을 핵심 지표로, 경고 문구를 "판정"이 아닌 "주의 신호"로 표현, 대화방별 "이 대화는 괜찮아요" 표시 기능 |
| **악성 앱과 같은 구조(남의 메시지를 읽음)라는 윤리 문제** | 본인 동의 필수·숨김 동작 금지(상시 상태 알림 표시)·인터넷 권한 없음·가족 공유는 본인이 직접·언제든 끄고 데이터 전체 삭제 가능 (4.7 참고) |
| 가족이 경고를 늦게 알거나 모름 (B안의 대가) | 경고 화면에서 공유 버튼을 가장 눈에 띄게 배치, 7.2 대상자 확인에서 충분성 점검, 부족하면 다음 버전에서 A안 검토 |
| 가족이 몰래 설치해 감시 도구로 쓰일 위험 | 설치한 기기의 본인이 직접 동의 화면을 거쳐야만 동작, 상시 표시 알림으로 감시 중임을 숨길 수 없게 함 |
| 비슷한 서비스가 이후 발견됨 | 차별점(한국어 메신저·대화 흐름 기반 위험 신호 판정·인터넷 권한 없는 기기 내 처리) 기준으로 비교표 작성 후 계속 진행 |
